# 定向通知与工作台待办设计

## 背景

项目已经具备合同签署、托管付款、里程碑交付审核等协作流程，但消息中心里的项目通知还没有明确收件人，甲方和乙方也需要进入项目详情页才知道下一步该做什么。为了让流程更像真实产品，本阶段补齐“谁需要被提醒”和“工作台顶部该提示什么”。

## 目标

- 项目通知支持定向发送给甲方或乙方。
- 消息中心默认只展示当前用户相关的通知。
- 甲方工作台展示最多 3 条关键待办。
- 乙方工作台展示最多 3 条关键待办。
- 待办点击后进入对应项目详情页。
- 继续使用 localStorage 作为可演示数据源，保留以后接入 Supabase 的空间。

## 非目标

- 不做真实实时推送。
- 不接短信、邮件、Web Push。
- 不做复杂通知偏好设置。
- 不重构现有消息中心视觉结构。

## 方案选择

采用“轻量待办 + 定向通知”方案。

通知仍由 `engagementService` 管理，在现有 `NotificationItem` 上增加可选字段：

- `recipientId`
- `recipientRole`
- `actionLabel`
- `priority`

这样旧通知不会失效，新通知可以按用户过滤。工作台待办单独由 `projectTodoService` 生成，不额外持久化，直接根据项目、应征、合同、托管和进度状态实时推导。

## 通知触发点

- 选定创作者：通知乙方合作已开始。
- 生成合同草稿：通知乙方待签合同。
- 甲方签署合同：通知乙方待签合同。
- 乙方签署合同：通知甲方合同已生效。
- 乙方提交交付：通知甲方待确认交付。
- 甲方要求修改：通知乙方待修改。
- 甲方确认节点：通知乙方节点已确认；如托管释放成功，说明款项已释放。

## 工作台待办规则

甲方待办：

- 项目已选定乙方但未生成合同：提示生成合同草稿。
- 合同存在但甲方未签署：提示甲方确认签署。
- 已选定乙方但没有托管计划：提示创建托管计划。
- 托管计划为草稿：提示确认托管。
- 当前节点状态为 `waiting_owner`：提示确认交付或要求修改。

乙方待办：

- 合同存在但乙方未签署：提示乙方确认签署。
- 当前节点状态为 `waiting_aigcer`：提示提交当前节点交付。
- 当前交付记录状态为 `changes_requested`：提示根据反馈修改后重新提交。

待办按优先级排序，只展示最多 3 条：

1. 合同签署
2. 交付审核或修改
3. 托管付款

## 页面设计

在 `DashboardClient` 和 `DashboardAigcer` 统计卡片下方增加一个轻量“待办事项”区域。

每条待办包含：

- 标题
- 简短说明
- 关联项目名
- 操作按钮

空状态不显示大块卡片，只用一行简短提示，避免工作台变臃肿。

## 错误处理

- 通知过滤兼容旧数据：没有 `recipientId` 的通知继续显示。
- 待办生成时如果合同或托管查询失败，忽略该项，不阻塞工作台。
- 项目详情触发通知失败时不阻塞主流程。

## 测试策略

- `engagementService`：测试定向通知创建、按用户过滤、旧通知兼容、已读状态。
- `projectTodoService`：测试甲方合同待办、托管待办、待确认交付；测试乙方待签合同、待提交节点、待修改交付。
- 页面通过构建和浏览器 smoke test 验证待办区域可见、按钮跳转正常。
